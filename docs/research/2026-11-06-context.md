# Context audit: 2026-11-06

This record preserves the evidence and user decisions that preceded the rpgmigrate implementation.
Repository states and issue counts refer to the audit on 2026-11-06.
This record explains the failures that the design must prevent.

## User decisions and approved scope

The user approved the design after the repository, issue, storage, and transport reviews.
These decisions supersede earlier assumptions in the conversation:

- We use `origin/v0.18-fixes` as the primary behavioral baseline.
- We name the executable `rpgmigrate`.
  Existing subcommands, CLI options, environment compatibility, and meaningful output contracts remain requirements.
- We leave existing pgcopydb migrations and work directories untouched.
  Legacy import, conversion, resume, and cleanup are outside scope.
  Native `--resume` and `--restart` operate only on recognized rpgmigrate state.
- We can choose any storage backend that meets the approved guarantees.
  The user requested faster storage when measurements support it.
  We do not require SQLite format compatibility.
- We prioritize WAL application performance because customers reported slow replay.
  That feedback establishes priority, not a measured throughput baseline.
- We implement `durable`, `replay-safe`, and `relaxed` modes, with `durable` as the default.
  Documentation must explain each mode's failure guarantees, recovery requirements, and performance implications.
  Relaxed mode requires finite transaction-count and encoded-byte loss caps across the entire migration run.
- We retain a narrow libpq ownership boundary and PostgreSQL schema utilities in the initial design.
  We use target checkpoints committed with replay effects, plus explicit recovery after uncertain COMMIT outcomes.
- We adapt the operator separately for the new executable and native state.
  An image change must not switch an existing pgcopydb migration to rpgmigrate.

The approval does not establish implementation readiness or measured performance.
Replay-safe recovery requires surviving durable journal storage.
Relaxed mode permits loss of acknowledged changes within its explicit reservation.
A flush interval is a scheduling target, not a guaranteed loss duration.
All modes must establish durable completion before successful cutover.

## Failures, required invariants, and existing regressions

The following mappings preserve behavioral requirements without requiring SQLite-specific assertions.
An LSN identifies a WAL position, not a unique decoded event.
CDC means change data capture.

### Transaction order and event identity

[Operator #356](https://github.com/ydixken/pgcopydb-operator/issues/356) documents omitted transactions when BEGIN order differs from COMMIT order.
[Operator #357](https://github.com/ydixken/pgcopydb-operator/issues/357) reports six target rows from 1,000 source rows after same-LSN events collapsed.
Preserve commit order, every event ordinal, transaction completeness, and retransmission identity.
The fork's [interleaved-commit](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-interleaved-commits/copydb.sh) and [COPY multi-insert](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-copy-multi-insert/copydb.sh) fixtures exercise these failures.

### Target COMMIT and unknown outcomes

[Fork #6](https://github.com/ydixken/pgcopydb/issues/6) reports completion before a pipelined COMMIT succeeds.
[Operator #359](https://github.com/ydixken/pgcopydb-operator/issues/359) reports origin advancement despite aborted target work.
The audit did not establish that report as a general PostgreSQL replication-origin defect.
Associate completion evidence with committed data, and reconcile unknown outcomes before replay or acknowledgement.
The fork's [origin-abort suite](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-origin-abort/copydb.sh) covers rejected COMMIT, process death, backend termination, and grouped transactions.
Its mitigation does not prove every broken-connection or server-crash interleaving safe.

### Feedback, keepalives, and drain completion

[Upstream #1048](https://github.com/dimitri/pgcopydb/issues/1048) reports requested endpos replacing measured replay progress.
[Fork #8](https://github.com/ydixken/pgcopydb/issues/8) documents a filtered-WAL feedback stall and its guarded fix.
Track received, journal-durable, target-visible, target-durable, and source-acknowledged progress separately.
Server WAL end and requested endpos are not evidence of completed target work.
Retain the [keepalive](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-keepalive/copydb.sh) and [receive group-commit](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-receive-group-commit/copydb.sh) cases.

### Journal recovery and segment reclamation

[Operator #376](https://github.com/ydixken/pgcopydb-operator/issues/376) reports missing data after advancement past an undrained segment.
Keep segment closure, complete consumption, and safe deletion as separate states.
Reject corruption inside required durable history rather than silently skipping it.
The fork's [live-rotation fixture](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-file-rotation-live/verify.py) requires the problematic record arrangement and exact nonempty data equality.
The [commit-order resume fixture](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-commit-order-resume/copydb.sh) damages replay WAL and requires reconstruction.
The [pgoutput resume fixture](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-pgoutput-resume/copydb.sh) checks interrupted receive, spool integrity, and ordered data digests.

### Snapshot loss and COPY completion

[Operator #378](https://github.com/ydixken/pgcopydb-operator/issues/378) documents incompatible snapshot and slot reuse after an interrupted base copy.
[Upstream #1063](https://github.com/dimitri/pgcopydb/issues/1063) reports split-copy resume truncation without an independently executed reproduction in this audit.
Preserve snapshot/stream consistency and resolve target/local completion gaps before reusing partial work.
The fork preserves fully completed tables but truncates and recopies partially completed split tables.
Retain [split-table resume](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/split-table-resume/copydb.sh) and [snapshot-loss refusal/restart](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/follow-resume-snapshot/copydb.sh) coverage.

### Row semantics and schema verification

[Operator #358](https://github.com/ydixken/pgcopydb-operator/issues/358) reports incomplete replay of multi-table TRUNCATE.
[Operator #249](https://github.com/ydixken/pgcopydb-operator/issues/249) shows that matching leaf data does not prove matching partition topology.
Preserve every selected relation, exact NULL/TOAST meanings, and one-row effects for keyless duplicate rows.
Retain [multi-table TRUNCATE](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-truncate-multi/copydb.sh) and [replica-identity FULL](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-replica-identity-full/copydb.sh) regressions.
Use the operator's [fingerprint mutation tests](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/test/e2e/coverage_fingerprint_test.go) to check verification itself.

### PostgreSQL resource ownership

[Operator #362](https://github.com/ydixken/pgcopydb-operator/issues/362) reports a `PGresult` double-free.
[Operator #364](https://github.com/ydixken/pgcopydb-operator/issues/364) reports a `PGconn` double-finish and leaked results.
Give each connection, result, and COPY buffer one owner with explicit cleanup.
Retain the [drain-error](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-receive-drain-error/copydb.sh) and [dying-source reconnect](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/cdc-receive-reconnect-dying-source/copydb.sh) fault injections.
Rust can prevent ownership errors in safe code, but an unsound FFI wrapper can recreate them.

### Missing evidence and monitoring

[Upstream #1046](https://github.com/dimitri/pgcopydb/issues/1046) reports successful comparison despite differing data.
[Operator #287](https://github.com/ydixken/pgcopydb-operator/issues/287) reports unreadable state counting as successful completion.
[Upstream #1038](https://github.com/dimitri/pgcopydb/issues/1038) documents progress polling that changes persisted filters.
Keep matched, different, failed, and unchecked outcomes distinct, and make monitoring observational.
Retain [filter command composition](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/filtering/copydb.sh) and the operator's [negative outcome checks](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/test/e2e/coverage_outcome_test.go).

### Independent phases and bounded recovery

The fork fixes omitted large-object work, trailing bytes after recopy, stale worker elections, and incomplete multidatabase resume.
Reconcile each phase against actual target effects rather than treating table completion as migration completion.
Retain [large-object resume](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/large-objects-resume/copydb.sh) and [all-databases resume](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/all-databases-resume/copydb.sh).
[Operator #243](https://github.com/ydixken/pgcopydb-operator/issues/243) documents retry blocked by an orphan target backend.
The fork's [orphaned-backend regression](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/orphaned-target-backend/copydb.sh) anchors cancellation and recovery requirements.

### Memory, catalog identity, and backpressure

SQLite originally addressed [catalog duplication](https://github.com/dimitri/pgcopydb/issues/532) and [whole-transaction memory exhaustion](https://github.com/dimitri/pgcopydb/issues/511).
Its replacement must retain bounded memory and efficient lookup.

[Upstream #493](https://github.com/dimitri/pgcopydb/issues/493) documents circular waits between data pipes and transaction metadata.
Bounded queues need a progress argument when consumers stall.
[OID collisions](https://github.com/dimitri/pgcopydb/issues/772), [attribute-number gaps](https://github.com/dimitri/pgcopydb/issues/679), and [duplicate catalog rows](https://github.com/dimitri/pgcopydb/issues/889) require explicit identity and cardinality models.
The audit found no repeatable throughput gate that proves bounded resource use for the new design.

## Operator contracts and development methods

The operator consumes commands, JSON schemas, exit codes, log messages, PostgreSQL application names, and state across invocations.
Its [argument renderer](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/internal/pgcopydb/args.go) also probes a literal help sentence for deferred indexes.
Its [progress reader](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/internal/progress/progress.go) uses an exact version allowlist.
The audit found no production operator code that directly opens SQLite databases.
The pinned fork's [sentinel](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/src/bin/pgcopydb/sentinel.c) is local SQLite state, despite legacy source-table wording in logs.

The initial CLI inventory used local main's parsers, which accept options absent from generated help.
Derive implementation fixtures from the fixes branch's parsers and actual consumers.
Preserve libpq connection semantics, including service/password files, authentication, and TLS verification.
Existing coverage includes [PostgreSQL 9.6 with test_decoding](https://github.com/ydixken/pgcopydb/blob/86bf908adca02d87063849dae775a02c1659c829/tests/follow-9.6/copydb.sh).
That fixture does not establish every intermediate version pair.

Transfer the operator's [strict fixture metadata](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/test/e2e/coverage_case_test.go), independent fingerprints, and failure-reason assertions.
Use observable database state for concurrency ordering and owned identities for cleanup.
Retain [tests of build configuration](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/test/buildconfig/buildconfig_test.go) so missing prerequisites and skipped cases cannot appear successful.
The operator's [release gate](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/.github/workflows/release.yml) excludes chaos/flaky cases and does not cover its entire version matrix.
Its [promotion workflow](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/.github/workflows/promote.yml) triggers another publication, so exact-artifact promotion remains a rpgmigrate requirement.

The operator limits agents to local formatting/lint and CI functional tests in its [instructions](https://github.com/ydixken/pgcopydb-operator/blob/639bdf997f2ed32b6e0b88420455428cb5112c06/AGENTS.md).
That repository-specific rule does not automatically define rpgmigrate's local test policy.
We adopt ponytail full, humanizer/deslop, STE100, current documentation, and recorded verification evidence.
The operator names humanizer as its prose skill, which overlaps with deslop but is a separate skill.

## Performance questions for implementation

These questions define experiments, not performance claims:

- Does a segmented journal outperform packed redb or optimized SQLite under the same durability and recovery contract?
- How much apply time comes from decoding, intermediate serialization, allocations, SQL execution, pipeline waits, and commits?
- Do guarded UPDATE batches or COPY staging improve UPDATE-heavy workloads without changing row semantics?
- Can independent transactions execute concurrently while preserving dependencies and source commit order?
- Does replay-safe batching improve sustained target throughput, or mainly reduce source acknowledgement latency?
- How do giant transactions, hot keys, slow readers, pruning, and disk exhaustion affect memory and recovery time?
- What target-checkpoint overhead appears under realistic commit rates, WAL settings, and synchronous standby policies?
- Do improvements survive repeated complete migrations and the operator's actual process topology?

Measure visible and durable apply latency separately, alongside committed rows/transactions, backlog growth, CPU, peak memory, physical writes, and recovery time.
Record source and target versions, workload, commit SHA, artifact digest, storage conditions, and durability settings with each result.
Compare the optimized fork and candidate under equivalent guarantees.
Report relaxed-mode results with their loss limits and failure assumptions.
